根據提供的資料，團隊最終沒有採用自適應分段（adaptive segmentation）方法，主要是因為過去的實驗證明其效果不佳且存在根本性的技術缺陷。目前的「固定80行窗口 + 驗證/修復」策略是一種務實的替代方案。

以下是詳細的演進過程：

### 1. 早期探索：動態與固定分塊的辯論

最初，團隊意識到將完整逐字稿一次性處理會因上下文過長而失敗（`[L1-0429-122]`），因此必須採用分塊（chunking）策略。當時主要有兩種思路：

*   **固定分塊 (Fixed Chunking)**：以固定行數（如3行、5行）切割文本。
*   **動態分塊 (Dynamic Chunking)**：由 LLM 根據語義完整性自行決定區塊大小，避免破壞上下文，例如將問題與答案分開（`[L1-0422-007]`）。

團隊決定對這兩種方法進行比較實驗，以評估其成本與品質（`[L1-0422-020]`, `[L1-0429-029]`, `[L1-0429-065]`）。

### 2. 自適應窗口實驗的失敗

團隊進行了一項自適應窗口（adaptive window）的實驗，這屬於動態分塊的一種實現。然而，該實驗被放棄，原因如下：

*   **結果惡化**：實驗直接導致結果變差，表現為「拒絕 (rejected) 數量變高，驗證 (verify) 數量變少」，意味著產出的內容可信度降低（`[L1-0506-003]`, `[L1-0506-014]`）。
*   **無法精確定位邊界**：自適應方法的核心問題在於它很難準確預測語義段落的結束點。任何不準確的切割都需要回退進行邊界校正，這反而抵銷了自適應帶來的靈活性優勢，使其變得不切實際（`[L1-0506-003]`, `[L1-0506-014]`）。
*   **實驗被廢棄**：由於效果不佳，該實驗的程式碼已被覆蓋（`[L1-0506-003]`）。

### 3. 最新階段：採用固定窗口 + 驗證/修復機制

在自適應方法失敗後，團隊確立了目前的處理架構：

*   **由上而下 (Top-down) 的固定窗口**：採用 `Context Planner` 將逐字稿切分為固定的80行窗口，再交給 `Segment Agent` 進一步處理成 `segments` 和 `idea units`（`[L1-0506-001]`）。選擇固定窗口的主要原因是為了**方便除錯**（`[L1-0506-007]`）。
*   **驗證與修復 (Verify/Repair)**：固定窗口不可避免地會切斷語義完整的段落。為了解決這個問題，系統加入了後續處理機制：
    *   **處理遺漏 (Gaps)**：系統會檢查在提取 `idea units` 後是否有被遺漏的逐字稿行，並將這些「間隙」作為低品質的原始文本加回來，以確保資訊不丟失。未來計劃開發更正式的修復機制（`[L1-0506-005]`, `[L1-0506-010]`）。
    *   **處理截斷 (Truncation)**：透過 `batch` 機制，將被固定窗口截斷的 `segment` 與後續的 `segment` 合併，以修復其完整性（`[L1-0506-028]`）。

### 總結與未來展望

總而言之，團隊放棄自適應分段是因為**實驗證明其無法準確預測邊界，導致結果惡化**。目前的固定80行窗口是一個為了**穩定性與可除錯性**而採用的權宜之計，並搭配「驗證/修復」機制來彌補其缺點。

這個問題仍被視為一個**待解決的議題**（`[L1-0506-007]`）。團隊內部也存在不同看法，例如有人認為追求完美分段的效益可能有限，因為下游的 LLM 有能力處理較大的不完美文本塊（`[L1-0506-011]`）。為了更客觀地評估未來的分段方法，團隊決定建立一個手動標記的「真實標記 (ground truth)」資料集（`[L1-0506-013]`）。
