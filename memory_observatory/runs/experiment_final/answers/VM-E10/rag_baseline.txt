根據提供的資料，目前 short-term 和 long-term memory 是**分開、平行更新**的，兩者都直接從會議逐字稿獲取資訊，而不是將逐字稿先路由到 short-term，再由 short-term 更新 long-term。

主要原因如下：
1.  **避免資訊延遲**：如果採用 short-term 更新 long-term 的串行方式，long-term memory 將無法即時跟上最新的會議狀態。例如，上週討論的新主題 C 和 D，如果需要等它們從 short-term 中消失後才能進入 long-term，那麼 long-term 記憶就會一直處於落後狀態 ([rag-0408-L106-L125])。
2.  **功能與資料粒度不同**：團隊將 short-term 和 long-term 視為兩個功能不同的獨立資料庫。Short-term 負責保存近期會議的**較多細節**，而 long-term 則負責儲存跨越更長時間的**大綱和脈絡**。讓 long-term 系統去處理 short-term 總結過的內容，再進行二次總結，被認為是沒有必要的 ([rag-0408-L106-L125])。

### 更新關係的演進歷史

1.  **早期概念 (2024年3月)**：
    *   最初，團隊就設想 short-term 和 long-term 是分開的機制。Short-term 專注於近期（如近三次）會議的具體事項，特別是待辦事項（to-do），而 long-term 則用來記錄整個研究從頭到尾的架構變化、目標和主題等更宏觀的脈絡 ([rag-0307-L31-L50], [rag-0325-L121-L140])。
    *   當時曾有過「short-term 的東西是否能延展成 long-term 的架構」的討論，但結論是「應該是分開的」([rag-0307-L31-L50])。團隊也認識到，未來 long-term 和 short-term 可能需要結合，但當前的開發是先將兩者分開建立 ([rag-0307-L31-L50])。

2.  **設計確立 (2024年4月)**：
    *   團隊明確討論了更新流程，並確立了平行更新的設計。核心論點是，如果 long-term 的更新依賴於 short-term，會導致資訊滯後 ([rag-0408-L106-L125])。
    *   因此，團隊決定讓 long-term 和 short-term 直接從同一份逐字稿來源進行更新，將它們比喻為「兩個分開的資料庫」，一個保存細節，一個保存大綱。這樣 long-term 可以獨立判斷逐字稿中的哪些內容適合放入其記憶中，無需經過 short-term 的中間處理 ([rag-0408-L106-L125])。
    *   這個時期的規劃也體現在實驗設計中，團隊計劃進行消融研究（ablation study），分別測試「只有 short-term」、「只有 long-term」以及「完整系統」的效果，這也佐證了兩者是可獨立運作的模組 ([rag-0429-L121-L140])。

3.  **近期實作 (2024年5月)**：
    *   目前的開發進度證實了這個平行架構。團隊正在開發的 long-term 系統（包含 L1, L2, L3 層級）是獨立的，其更新流程是直接處理逐字稿，將其分解為 idea units，再生成 L1 node ([rag-0506-L46-L65])。
    *   在描述 long-term 系統的運作時，明確提到「這個是 long term 的系統這是分開的」，再次強調了其獨立性 ([rag-0506-L46-L65])。
