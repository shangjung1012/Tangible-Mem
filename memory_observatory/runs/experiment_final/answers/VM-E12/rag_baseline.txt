### 為什麼先做 Update，晚一點才做 Retrieve？

團隊在開發初期，策略上選擇先專注於記憶的**更新（Update）**機制，之後再處理**擷取（Retrieve）**的部分。

*   **L1 Evidence Seeds:**
    *   在 `meeting=0307` 的討論中，團隊成員明確表示，當時的開發進度主要集中在「update memory 的部分」，而「還沒有設計如何從記憶取出來」。這表明團隊將記憶系統的開發分為至少兩個階段：更新與擷取，並決定先完成前者 `(meeting=0307, lines=16-35)`。
    *   團隊的計畫是先分別建立短期、長期等不同記憶體的更新方式，待更新機制大致建立後，下一步才是設計如何取用這些記憶 `(meeting=0307, lines=31-50)`。

### 後來 Retrieve 的設計演變為何？

Retrieve 的設計經歷了從「由程式邏輯決定」到「由 LLM 自主決定」的演進。

*   **L1 Evidence Seeds (早期設計):**
    *   最初的設想是，當一句話進來時，程式會同時去短期記憶和長期記憶中尋找相關內容，然後將找到的資料與原始的問句結合，再一起送給 LLM 生成回應 `(meeting=0408, lines=61-80)`。在這個模式下，擷取哪個記憶體是由開發者預先設定的程式邏輯所控制。

*   **L2 Evolution Context (後期設計 - 最新階段):**
    *   後來的設計引入了 Gemini 的 **Function Calling** 功能。新的流程變為：
        1.  將使用者的問題（例如：「這週的 TODO 是什麼？」）直接傳送給 LLM (Gemini)。
        2.  同時提供給 LLM 兩個由團隊開發的函式（function）作為工具：一個用於擷取短期記憶，另一個用於擷取長期記憶。
        3.  由 LLM 根據問題的語意，**自行判斷**應該呼叫哪一個函式（或都不呼叫）。
        4.  程式接收到 LLM 的指令後，執行對應的函式來取得記憶內容，再將結果回傳給 LLM，讓它生成最終的回答 `(meeting=0408, lines=61-80)`。
    *   這個設計的優點是將「決定使用哪種記憶」的判斷權交給了更具智慧的 LLM，使其能更靈活地應對不同的查詢情境 `(meeting=0408, lines=121-134)`。此外，這些提供給 LLM 的函式還可以包含時間範圍等參數，讓 LLM 能進行更精細的記憶查詢 `(meeting=0408, lines=121-134)`。
