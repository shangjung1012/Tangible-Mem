目前的系統被認為是一個單體系統（monolithic system），即將一個複雜的 prompt 從頭到尾交給 Gemini 處理，這種方式引發了一些問題，從而推動了架構演變的討論。

主要的考慮因素與演進步驟包括：

1.  **解決測試與除錯的困難**：一個採用 agent 架構的關鍵理由是它支援獨立的元件測試。目前的單體系統下，任何改動都需要從頭到尾運行整個流程才能看到結果，無法單獨測試某個環節（例如斷行功能）的效果。而多 agent 架構則允許獨立測試和調整各個 agent，有助於分析和除錯。
    *   **來源**：[0429 | L1-0429-148]

2.  **提升系統控制性**：目前的作法是將整個端到端的流程交給 Gemini，導致開發者難以對其中的邏輯和狀態進行精確控制（例如，在特定函式被呼叫時對一個變數進行計數）。因此，有人建議採用一個由程式開發者控制的系統架構，讓 Gemini 專注於執行離散、模組化的任務，以確保更好的控制力。
    *   **來源**：[0429 | L1-0429-119]

3.  **目前的開發策略**：團隊的共識是，在決定是否要重構成為多 agent 架構之前，應先嘗試修復和改善目前的 prompt，因為它目前的表現與預期行為有很大的差距。在改進 prompt 後，再評估是否有必要轉向 agent 架構。
