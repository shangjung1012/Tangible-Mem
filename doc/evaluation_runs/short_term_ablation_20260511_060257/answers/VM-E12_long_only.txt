根據提供的 context，關於記憶體更新（update）與檢索（retrieval）的資訊整理如下：

### 整體策略演變

專案初期的計畫是先建立更新方法，再處理檢索（L1-0307-024）。然而，後續決定將研究重點放在檢索（retrieval）問題上（L1-0325-056）。這個轉變發生在 2026 年 3 月，後者為較新的決策。核心挑戰被定義為 agent 應如何權衡與組合來自工作、短期和長期三種記憶體的資訊以生成最佳輸出（L1-0325-056）。

### 記憶更新 (Memory Update)

關於記憶更新的討論，主要可以歸納在 L2 主題 `L2-memory-update-semantics` 之下。

*   **L2 Topic**: `L2-memory-update-semantics` (memory update semantics)
    *   **L1 Evidence**:
        *   **核心架構**: 記憶更新流程已改為採用以 Gemini Tool Calling 為核心的架構。此方法讓 Gemini 將逐字稿視為資料庫，並動態決定要讀取多少內容，避免了固定的資料分塊。Gemini 主要使用 `Read` 和 `Write` 兩個函式來存取原始逐字稿和現有記憶體（L1-0422-001）。
        *   **基本單位**: 記憶更新的基本單位被確立為 `idea unit`。一個 `idea unit` 經 agent 標記後成為 `candidate`，接著被用來更新一個記憶節點（L1-0506-016）。
        *   **獨立更新**: 團隊決定短期記憶和長期記憶將獨立更新，放棄了之前短期記憶內容會轉存為長期記憶的設計（L1-0408-036）。
        *   **時間軸保存**: 目前支持時間導向的架構，即為每次會議創建新的、獨立的節點，以保存一個清晰、不可變的時間軸，這對 LLM 來說更容易解讀（L2-memory-update-semantics 的 current_state）。
        *   **衰減機制**: 設計上決定將 `importance` 分數保持靜態，作為節點創建時的歷史參考。記憶的衰減改由一個獨立的 `activation` 參數處理（L1-0506-030）。
        *   **待解問題**: 為了處理記憶節點因資訊混合而趨同（node convergence）的問題，團隊的解決方法已從簡單策略演變為對核心架構的探討（L1-0429-133）。

### 檢索 (Retrieval)

*   **核心挑戰**: 如上所述，檢索被視為專案最大的問題，關鍵在於如何權衡與組合來自三種不同記憶體（工作、短期、長期）的資訊（L1-0325-056）。
*   **檢索流程**:
    *   檢索流程的設計是先將使用者查詢與 L1 節點進行比對。
    *   然後，系統會取回匹配的 L1 節點及其對應的父層 L2 和 L3 摘要。
    *   這樣做的目的是為了同時提供具體的細節（L1）和高層次的上下文（L2/L3）（L1-0408-006）。
    *   在時間導向的架構下，檢索時可以透過追蹤不同會議中的匹配想法單元，並上溯至其 L2/L3 父節點，來為 LLM 提供一個想法跨越多場會議的時序脈絡（L2-memory-update-semantics 的 current_state）。
